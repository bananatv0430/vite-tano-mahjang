たの麻雀アプリ：機能一覧とリファクタリング記録
================================================

このファイルについて
--------------------
現時点でソースコードから確認できる主な機能と、今回のリファクタリングで整理した箇所を記録します。
仕様書ではなく、ソースを読むための案内です。運用・画面の細かな挙動は実際のアプリで確認してください。

アプリの主な機能
----------------

1. トップ画面（frontend/src/pages/Main.jsx）
   ・ランキングの表示
   ・直近の対局履歴の表示
   ・オンライン／オフラインなどの対局モードに応じたデータ表示

2. 対局成績
   ・日付別の対局結果と半荘ごとの成績表示（ResultsByDate.jsx）
   ・全体の集計表示（ResultsTotal.jsx）
   ・プレイヤー別の成績表示（Player.jsx）
   ・対局データの登録、複数半荘の入力（DataRegister.jsx）
   ・登録済み対局の編集・削除（DataEditDelete.jsx）
   ・点数、順位、ルール、参加者の入力と結果プレビュー

3. 麻雀ルール案内・点数計算
   ・役一覧とサンプル牌姿（RuleList.jsx、ruleListExamples.js）
   ・点数早見表（RuleScore.jsx、RuleScoreMobile.jsx）
   ・符計算ガイド、フローチャート、牌姿入力による符・役・点数算出（RuleFu.jsx、TileInput.jsx）
   ・団体ごとのルール比較（RuleOrg.jsx、ruleOrgData.js）

4. その他のページ
   ・スケジュール（OtherSchedule.jsx）
   ・ニュース（OtherNews.jsx）
   ・操作・更新ログ（OtherLog.jsx）

5. サーバー側（backend/workers）
   ・Cloudflare WorkerでAPIを提供し、D1データベースから対局・プレイヤー・ルール情報を取得・更新
   ・R2に保存したプレイヤー画像の配信
   ・プレイヤー、対局、結果、ランキング、ログ、ルールのAPIルート
   ・フロントエンドへのAPI通信は frontend/src/utils/apiFetch.js に集約

ここまでに整理した内容
----------------------

・役一覧ページ
  - 役のサンプル牌データを RuleList.jsx から ruleListExamples.js に分離
  - 共通の牌画像表示を YakuTileImages.jsx にまとめ、繰り返し表示を共通化

・符計算ページ
  - 牌姿からの符・役・翻・点数計算や入力解析を fuCalculation.js に分離
  - フローチャートの分岐計算を fuFlowLogic.js に分離
  - フローチャートの設問・表示設定を fuGuideData.js に分離

・団体別ルール比較
  - 団体名、リンク、比較項目、ルール値を ruleOrgData.js に分離

・対局登録／編集
  - 4人の参加者選択欄を EntryPlayerSelectors.jsx に共通化
  - 半荘入力行の一覧を EntryRoundList.jsx に共通化
  - 採用ルールの点数表示を EntryRuleSummary.jsx に共通化
  - 入力値の検証を useEntryFormModel.js に集約
  - 半荘プレビューのページ送りを useRoundPagination.js に集約
  - 参加者変更、得点・順位更新、入力フォーカス、半荘の並べ替えを useRoundInteractions.js に集約
  - 初期半荘データの生成を gameUtils.js の buildEntryRound に追加
  - DataRegister.jsx と DataEditDelete.jsx は順位の自動更新タイミングが異なるため、その差を維持

・共通データ取得
  - プレイヤーとルールの取得・正規化を useLoadReferenceData.js に集約
  - API応答が配列、または data プロパティ内の配列である形式の両方を処理
  - 登録画面と編集画面から共通フックを利用

・バックエンドの共通整形
  - 曜日と対局モードの表記処理を backend/workers/utils/format.js に置き、対局・結果ルートから利用

・対局結果のAPIデータ整形（今回追加）
  - JOIN結果を日付・半荘・参加者ごとにまとめる処理を backend/workers/utils/resultGroups.js に共通化
  - 年別結果、直近結果、日付指定結果の各APIで共通関数を利用
  - 各APIが返す日付・曜日・対局モード・ルール・参加者のデータ項目は従来の形を維持する想定

・対局の保存処理（今回追加）
  - 新規登録と編集で重複していた半荘・参加者成績の保存処理を games.js の insertGameRounds に共通化
  - 新規登録は入力された順位点を保存し、編集はルールから順位点を再計算する違いを呼び出し側に残す

・トップ画面のデータ取得フック分割（今回追加）
  - ランキング取得を useLoadRankings.js、直近履歴取得を useLoadRecentMatches.js に分離
  - Main.jsx の呼び出しと画面上の機能は維持

・プレビュー画面の共通操作（今回追加）
  - 画面幅に応じたモバイル判定と、Escキーによる結果プレビュー解除を usePreviewViewport.js に集約
  - 登録・編集・トップ・日付別結果の4画面で同じ判定幅（767px）とキー操作を使用

・プレイヤーアイコン表示（今回追加）
  - DataRegister／Playerで共通の代替アイコンと画像URL生成を playerIcons.js に集約
  - Main／ResultsByDateで共通のランキング向け代替画像も同じユーティリティへ集約
  - 既存の見た目（中立デザインとオレンジ色デザイン）を用途ごとに維持

・複数半荘の合計成績（今回追加）
  - プレイヤー別ポイントの合算と、合計順位の作成を gameUtils.js の共通関数に集約
  - トップ画面と日付別結果画面のプレビューで同じ集計を利用

・結果プレビューのページ送り（今回追加）
  - トップ画面と日付別結果画面のページ計算・半荘表示範囲・前後移動を useRoundPagination.js に共通化
  - PCは1ページに2半荘、モバイルは1半荘の表示を維持


・結果履歴の画面表示用変換（今回追加）
  - APIの半荘・参加者データを表示用に変換する共通処理を resultDisplayUtils.js に集約
  - トップ画面と日付別結果画面で共通の半荘・順位・アイコン・合計点変換を利用
  - 画面ごとの日付表示、並び順、必要な点数項目の違いは呼び出し側の指定で維持

・登録／編集APIの送信データ（今回追加）
  - 対局日・ルール・モード・半荘ごとの参加者成績を gamePayload.js で共通の送信形式に変換
  - 登録は順位点を含め、編集は従来どおり順位点を送らずサーバー側で計算
・登録／編集時の入力検証（今回追加）
  - 参加者4人の選択、重複、持ち点合計の確認を entryValidation.js に集約
  - 編集時のみ日付必須チェックを行い、登録・更新ごとのエラーメッセージを維持
・プレビューのスライドアニメーション（今回追加）
  - 4画面に重複していた前後ページ切替のキーフレームを previewAnimations.css に集約

残りの棚卸し結果（2026-11-12）
--------------------------

以下はソースを見直し、現時点では画面固有の処理として残す項目です。

・登録と編集の送信後処理
  - POST／PUTで送信内容と成功後の状態更新が異なるため、それらは各画面に残す
  - JSON解析とHTTPエラー本文の共通処理は requestJson に集約済み。画面ごとのエラー文は呼び出し側で指定

・年度別結果の初回取得と年度切替
  - fetchJson の通信処理に加え、API応答の年度一覧・試合データ変換を normalizeYearResults に共通化
  - 初回は初期年度を決め、切替時はキャッシュを見て取得する状態更新はそれぞれ維持

・団体別ルール画面のリサイズ処理
  - useMediaQuery でモバイル表示を判定
  - 残る resize 処理は表のスクロール領域の幅・高さを測る画面固有処理

・トップ画面と日付別結果の表示データ
  - 半荘・参加者の共通変換は resultDisplayUtils.js を利用
  - 日付表示、アイコン情報、並び順など画面ごとの出力差は各画面に残す

・未実装表示のある機能
  - 累計成績、スケジュール、お知らせ、符ガイドなどの「編集中／実装中」表示は既存の機能未実装箇所
  - これらはリファクタリングで仕様を決めたり実装したりする対象ではない

棚卸しでは、共通化可能な大きな重複は整理済みであることを確認しました。残る項目は上記の理由から現状のままとし、新たな挙動変更が必要な整理は画面確認を行う段階で判断します。
